## Answers to 16 Questions

### Section 1: Authentication & Authorization

#### Q1: Should local cluster registration require the user's Lyceum JWT token, or license key only?

**Answer: Option A - Require user JWT (user must be logged in)**

**Rationale:**
- ✅ Better security (prevents anonymous registration)
- ✅ Prevents license key sharing
- ✅ Consistent with existing Centcom authentication flow
- ✅ Enables user-specific features (multi-device tracking)

**Implementation:**
```typescript
// Registration requires Lyceum JWT from /api/centcom/auth/login
Authorization: Bearer <lyceum_jwt>
```

---

#### Q2: Should the `sync_token` returned by `/register` be short-lived (7 days) or long-lived (30+ days)?

**Answer: Long-lived (90 days) with automatic renewal**

**Rationale:**
- ✅ Minimizes re-registration overhead
- ✅ Centcom can run offline for extended periods
- ✅ Auto-renewal on heartbeat keeps token fresh
- ✅ 90 days matches quarterly license review cycle

**Implementation:**
- Sync token expires in 90 days
- Each successful heartbeat extends expiration
- If token expires, Centcom automatically re-registers using stored user credentials

---

### Section 2: Offline & Grace Period Handling

#### Q3: What should happen when a local cluster exceeds its grace period?

**Answer: Option B - Return `should_throttle: true` and Centcom enforces read-only mode**

**Rationale:**
- ✅ Consistent with design document
- ✅ Centcom has full control over local enforcement
- ✅ Lyceum provides guidance, Centcom decides UX
- ✅ User experience remains smooth (no hard blocks)

**Implementation:**
```json
// Heartbeat response when grace period exceeded
{
  "cluster_status": "grace_period_exceeded",
  "should_throttle": true,
  "warnings": [{
    "type": "offline_grace_period_exceeded",
    "message": "Cluster offline for 7 days. Read-only mode recommended.",
    "severity": "critical"
  }]
}
```

---

#### Q4: Should offline clusters be hidden from user portal, or shown with "Offline" status?

**Answer: Show with "Offline" status for transparency**

**Rationale:**
- ✅ Users need visibility into all their clusters
- ✅ Transparency builds trust
- ✅ Users can troubleshoot offline issues
- ✅ Provides context for "last seen" timestamps

**Implementation:**
- Cluster status: `"online"` | `"offline"` | `"grace_period"` | `"read_only"`
- Display badge in UI showing status
- Last seen timestamp always visible

### Section 3: Cluster Naming & Identification

#### Q5: Should Centcom auto-generate cluster names or allow customization?

**Answer: Auto-generate on first launch, allow editing in settings**

**Rationale:**
- ✅ Best of both worlds
- ✅ Zero-config for users who don't care
- ✅ Flexibility for power users
- ✅ Auto-generated names are descriptive ("Josh's MacBook Pro - Analytics")

**Implementation:**
- Default name format: `{hostname} - Analytics` or `{os} - {username} Cluster`
- Editable via `/api/v1/clusters/local/{cluster_id}` PATCH endpoint
- Max length: 255 characters

---

#### Q6: Should `machine_fingerprint` be primary identifier, or separate `cluster_id`?

**Answer: Lyceum-generated `cluster_id` (more flexible)**

**Rationale:**
- ✅ Handles machine upgrades gracefully
- ✅ UUID-based cluster_id never changes
- ✅ Machine fingerprint can change if hardware changes
- ✅ Better database normalization

**Implementation:**
- `cluster_id`: UUID generated by Lyceum on registration
- `machine_fingerprint`: 8-char SHA-256 hash for display/matching
- Both stored, cluster_id is primary key

---

### Section 4: Multi-Machine Scenarios

#### Q7: Can a single license have multiple local clusters (e.g., desktop + laptop)?

**Answer: YES - Allow multiple, aggregate metrics across all machines**

**Rationale:**
- ✅ Common use case (work laptop + home desktop)
- ✅ Enterprise users often have multiple machines
- ✅ Aggregate usage = more accurate limit enforcement

**Implementation:**
- No limit on number of registered clusters per license
- Usage aggregation:
  ```sql
  SUM(storage_used_gb) AS total_storage
  SUM(queries_this_month) AS total_queries
  ```
- Each cluster tracked individually, limits enforced on aggregate
- License limits still apply (e.g., 10GB total across ALL machines)

---

#### Q8: If user replaces machine (new fingerprint), should old cluster be auto-decommissioned?

**Answer: Auto-decommission after 30 days of inactivity**

**Rationale:**
- ✅ Handles machine replacement gracefully
- ✅ 30 days allows for temporary machine issues
- ✅ Prevents orphaned clusters
- ✅ Users can manually decommission if needed

**Implementation:**
- After 30 days of no heartbeat: `status` → `decommissioned`
- Decommissioned clusters excluded from usage aggregation
- Decommissioned clusters hidden from user portal (show in history)
- Manual "Decommission" button available for immediate cleanup

### Section 5: Admin Panel Features

#### Q9: What actions should admins take on local clusters in Unified Cluster Management?

**Answer: Admins should be able to:**
- ✅ View usage history (charts, trends)
- ✅ Force decommission (for abuse/troubleshooting)
- ✅ View connection logs (heartbeat history)
- ✅ Adjust grace period per-cluster (override license default)
- ✅ View machine info (CPU, RAM, OS)
- ⚠️ Reset usage metrics (only for billing corrections)
- ❌ Remotely access cluster (security risk, not supported)

**Implementation:**
- Admin endpoint: `GET /api/v1/admin/clusters/local/{cluster_id}`
- Actions available:
  - View details
  - Decommission
  - View logs (last 100 heartbeats)
  - Adjust grace period
  - Reset usage (requires admin confirmation)

---

#### Q10: Should admins see raw `machine_fingerprint` or truncated hash?

**Answer: Truncated hash only (8 chars) for privacy**

**Rationale:**
- ✅ Privacy-first approach
- ✅ 8 chars sufficient for identification/support
- ✅ Raw hash exposes hardware details (security risk)
- ✅ Full hash available only to superadmin (audit log)

**Implementation:**
- Display: `A3B4C5D6` (8 chars)
- Full hash stored in database
- Full hash visible only in superadmin audit interface
- Hover tooltip shows "Machine ID (truncated for privacy)"

### Section 6: Usage Metrics & Billing

#### Q11: Should local cluster usage count towards overall account quota (if user has cloud clusters)?

**Answer: Separate quotas (local vs cloud)**

**Rationale:**
- ✅ Simpler accounting
- ✅ Local clusters bundled with license (no additional billing)
- ✅ Cloud clusters billed separately
- ✅ Prevents confusion for users with both

**Implementation:**
- License limits apply only to local clusters
- Cloud clusters have separate pricing tiers
- Usage displayed separately in user portal:
  - "Local Cluster Usage: 3GB / 10GB"
  - "Cloud Cluster Usage: 125GB (billed)"

---

#### Q12: Should historical usage metrics be retained indefinitely or purged?

**Answer: Retain 90 days (detailed), then aggregate to monthly summaries**

**Rationale:**
- ✅ 90 days sufficient for trend analysis
- ✅ Monthly summaries for long-term tracking
- ✅ Reduces database size
- ✅ Meets compliance requirements

**Implementation:**
- `local_cluster_usage_history` table:
  - Detailed heartbeat data: 90 days retention
  - Automated purge job: daily cron
- `local_cluster_usage_monthly` table:
  - Aggregated monthly summaries (keep indefinitely)
  - Min/max/avg storage, total queries, uptime percentage
- Charts show 90-day detail, then monthly bars beyond that

### Section 7: Connectivity & Network Requirements

#### Q13: Is heartbeat-based status reporting (5-15 min intervals) sufficient?

**Answer: YES - Heartbeat is sufficient**

**Rationale:**
- ✅ Real-time not needed for analytics clusters
- ✅ 5-15 min provides good balance (freshness vs overhead)
- ✅ Offline queue handles network issues
- ✅ Reduces API costs

**Implementation:**
- Default interval: **10 minutes** (600 seconds)
- Configurable per license tier:
  - Trial: 15 minutes
  - Basic: 10 minutes
  - Professional: 5 minutes
  - Enterprise: 5 minutes (can go lower if needed)
- Offline tolerance: **3 missed heartbeats** before marking offline

---

#### Q14: Should we support HTTPS tunneling (Cloudflare Tunnel, ngrok) for admin remote access?

**Answer: NOT in Phase 1, consider for Phase 4 (Future)**

**Rationale:**
- ⚠️ Security complexity (authentication, authorization, audit)
- ⚠️ Liability concerns (admin accessing user machines)
- ⚠️ Not high-priority feature
- ✅ Heartbeat + logs sufficient for support

**Future Consideration:**
- If demand exists, implement secure tunneling with:
  - User opt-in (explicit consent required)
  - Time-limited access tokens (1-hour max)
  - Full audit logging
  - MFA required for admin
  - Read-only access only (no writes)

#### Task 1.3: Create/Enhance Registration Endpoint

**File:** `src/app/api/centcom/clusters/local/register/route.ts` (NEW)

```typescript
import { NextRequest, NextResponse } from 'next/server'
import { requireAuth } from '@/lib/auth-utils'
import { dbOperations } from '@/lib/supabase-direct'
import jwt from 'jsonwebtoken'

export async function POST(request: NextRequest) {
  const { success, user } = await requireAuth(request)
  if (!success) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })

  const {
    machine_fingerprint,
    license_key,
    cluster_name,
    machine_info,
    clickhouse_version,
    centcom_version,
    installation_id
  } = await request.json()

  // Validate license
  const { data: license } = await dbOperations.supabaseAdmin
    .from('license_keys')
    .select('*')
    .eq('key_code', license_key)
    .eq('assigned_to', user.id)
    .single()

  if (!license || !license.allows_local_cluster) {
    return NextResponse.json({ error: 'License does not support local clusters' }, { status: 403 })
  }

  // Upsert cluster
  const { data: cluster } = await dbOperations.supabaseAdmin
    .from('local_cluster_usage')
    .upsert({
      user_id: user.id,
      license_id: license.id,
      machine_fingerprint,
      cluster_name,
      installation_id,
      clickhouse_version,
      centcom_version,
      machine_os: machine_info.os,
      os_version: machine_info.os_version,
      machine_cpu_cores: machine_info.cpu_cores,
      machine_memory_gb: machine_info.memory_gb,
      architecture: machine_info.architecture,
      cluster_status: 'registered',
      last_heartbeat_at: new Date().toISOString()
    }, {
      onConflict: 'user_id,machine_fingerprint'
    })
    .select()
    .single()

  // Generate sync token (90 days)
  const syncToken = jwt.sign({
    cluster_id: cluster.cluster_id,
    machine_fingerprint,
    user_id: user.id
  }, process.env.CENTCOM_SIGNING_KEY, { expiresIn: '90d' })

  return NextResponse.json({
    cluster_id: cluster.cluster_id,
    status: 'registered',
    sync_token: syncToken,
    sync_interval_seconds: 600, // 10 minutes
    license: {
      license_type: license.license_type,
      max_storage_gb: license.local_cluster_limits.max_storage_gb,
      max_monthly_queries: license.local_cluster_limits.max_monthly_queries,
      expires_at: license.expires_at
    }
  }, { status: 201 })
}
```

#### Task 1.4: Enhance Heartbeat Endpoint

**File:** `src/app/api/centcom/clusters/local/heartbeat/route.ts` (NEW)

```typescript
export async function POST(request: NextRequest) {
  // Validate sync token
  const authHeader = request.headers.get('authorization')
  const token = authHeader?.substring(7)

  try {
    const decoded = jwt.verify(token, process.env.CENTCOM_SIGNING_KEY)
    const { cluster_id, machine_fingerprint } = decoded

    const {
      status,
      usage_metrics,
      last_sync_at
    } = await request.json()

    // Update cluster
    await dbOperations.supabaseAdmin
      .from('local_cluster_usage')
      .update({
        is_running: status.is_running,
        uptime_seconds: status.uptime_seconds,
        clickhouse_version: status.version,
        storage_used_gb: usage_metrics.storage_used_gb,
        storage_bytes: usage_metrics.storage_bytes,
        queries_this_month: usage_metrics.queries_this_month,
        project_count: usage_metrics.project_count,
        measurement_count: usage_metrics.measurement_count,
        table_count: usage_metrics.table_count,
        last_heartbeat_at: new Date().toISOString(),
        cluster_status: 'online'
      })
      .eq('cluster_id', cluster_id)

    // Insert history record
    await dbOperations.supabaseAdmin
      .from('local_cluster_usage_history')
      .insert({
        cluster_id,
        storage_used_gb: usage_metrics.storage_used_gb,
        storage_bytes: usage_metrics.storage_bytes,
        queries_count: usage_metrics.queries_this_month,
        project_count: usage_metrics.project_count,
        measurement_count: usage_metrics.measurement_count,
        table_count: usage_metrics.table_count,
        is_running: status.is_running,
        uptime_seconds: status.uptime_seconds
      })

    // Check limits and generate warnings
    const warnings = [] // ... limit checking logic

    return NextResponse.json({
      success: true,
      cluster_status: 'healthy',
      warnings,
      should_throttle: false,
      next_heartbeat_seconds: 600
    })
  } catch (error) {
    return NextResponse.json({ error: 'Invalid sync token' }, { status: 401 })
  }
}
```
